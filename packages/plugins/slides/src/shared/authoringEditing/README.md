# Slides authoring editing contract

`authoringEditing` owns the cross-process contract used to identify editable objects in a generated `deck.js` document. A target is the pair `slideKey + editKey`; keys are either explicit author facts or compiler-owned system identities and remain independent from page order, render order, source lines, content and geometry.

`manualEdits` is a versioned, strictly parsed authoring value block. Version 2 supports complete Text content replacement (string or styled text runs), text font size/color/emphasis/alignment/width, owned-image replacement/fit, Frame/Shape solid color, Shape/Image visual size, deletion of every editable author target and cumulative post-layout translation. Version 1 remains a read-only migration input and is normalized to version 2 at the codec boundary; every new source write emits version 2. Inline formula editing, table content and chart data remain outside the manual UI contract. The contract never accepts arbitrary property paths or generic JSON patches.

`SlidesManualEditCommand.operation` supports object operations targeting `slideKey + editKey`, atomic batches, undo/redo and page-index operations. Page indexes are interpreted only inside the command's exact `expectedBase` snapshot and never persist as identity. Static page creation/copy/delete/reorder rewrite the compose list; object insertion stores additions under the page's stable slideKey. The detailed rules below define each command.

`authoringEdit` is the RenderModel-side capability projection. The backend derives it from the admitted author tree before renderer text layout splits content into paragraphs or font runs. The `copy` capability is projected only for objects `readCopyableAuthoringValue` can write losslessly as an inserted object (plain-styled text, solid rect/ellipse without border/shadow/rotation/radius, plain document-owned images, outside groups); the backend copy uses the same predicate. Renderer selection and property controls consume explicit capabilities plus original text/fill facts; they must not infer write safety from the visual node shape. Editable rich author text is projected as `rich_text` with its original content and base style, and receives `set_text_content` and `set_text_style`. Formula-containing text remains `rich_text` without editable content and has no text-write capability. Renderer must never reconstruct author runs from finalized layout slices. Gradient/image fills are projected as `non_solid`, so the UI may replace them with a solid color without pretending it can edit their internal stops or assets.

Flex compilation flattens a decorated Frame into one background render node plus its descendant render nodes. `_authoringAncestorRefs` preserves the author hierarchy through DirectComposeInput and DeckSpec; RenderModel exposes it as `authoringAncestorRefs`. The list may contain only same-slide, non-duplicated Frame identities in outer-to-inner order. Renderer uses this compiler-owned relation to preview a Frame translation across its complete rendered subtree. It must not derive membership from source spans, layout diagnostic paths, overlap or geometry.

Quality and inspect derive `authoringFrameId` from the nearest explicit Frame ancestor through `resolveSlidesAuthoringFrameNodeId`. This is diagnostic context, separate from the flattened render `parentNodeId`; it neither adds an author parent type nor changes the persisted identity contract. Missing Frame identity does not permit inference from overlap or source paths.

Plugin migration v10 upgrades current DeckSpecs produced before this field existed. The one-time migration reads the old compiler's deterministic `layoutNodeId` hierarchy and writes `_authoringAncestorRefs`; normal RenderModel construction has no legacy dual-read path. Historical source revisions remain source-first and receive the current contract when restored or rebuilt.

Rules:

- `set_text_content` carries an explicit `targetKind: 'text' | 'shape'`. A Shape's string content belongs to that Shape identity, not a synthetic child text target. Shape content is stored alongside its fill, size and translation in the same manual record; Shape rich content remains unsupported. For targetKind=text the content is a complete string or text-run array; for shape it remains strictly a string. This does not enable shape text-style editing.

- keys use `^[A-Za-z][A-Za-z0-9_-]{0,63}$` so they are deterministic, readable and safe in source and render identities;
- `slideKey` is unique in one deck and `editKey` is unique in one slide authoring tree; system namespaces `sysp_`, `sysu_`, `sysr_` are compiler-owned;
- a node with `editKey` requires its slide to have `slideKey`;
- generated sources without keys receive system identities through the sandbox authoring-identity owner; old compiled revisions obtain the same facts from exact-source materialization;
- `RenderNode.id` remains a render-tree detail; persistence and commands use `authoringRef`.
- compiled `authoringRef` also carries `targetKind` so Renderer can distinguish a decorated Frame from a Shape; this field does not participate in identity and command targets still use only the two keys;
- flattened descendants carry their editable Frame ancestors separately from their own `authoringRef`; a child remains independently editable while also participating in each ancestor Frame translation;
- a RenderNode with `authoringEdit` must also carry `authoringRef`; the strict RenderModel codec rejects malformed or contradictory capability projections;
- Text replacement accepts the same text-only run structure as source, preserving unmodified style fields; formula-containing author nodes reject manual replacement. Range selection stays within the input session, and only the resulting complete author value crosses IPC. Rich content takes precedence over inherited object-level style in the same way as generated code;
- object-level Text style accepts a finite `fontSizePt` from 1 through 400, including decimals, and canonical `#RRGGBB` color values; omitted style fields retain their previous manual value. `SLIDES_MANUAL_FONT_SIZE_PT` is the shared min/max definition consumed by Renderer inputs/presets, operation validation, IPC admission and manual-edit parsing; consumers must not maintain separate range literals;
- visual size is a positive width/height pair in inches. A `set_visual_size` command may also carry a finite `translationDelta` in slide inches to preserve the opposite resize anchor; the backend accumulates it into the existing translation in the same revision. It is command data, not a new persisted field or schema version. Omitting it preserves the current origin; Shape/Image size is applied after Yoga layout, so nearby Flex siblings keep their authored occupancy and do not reflow during this deliberately limited edit;
- deletion is evaluated before Yoga. An atomic target removes only itself, while a Frame removes its complete author subtree. Every deletion record is exclusive and cannot retain translation, style, fill or size values;
- Shape and Frame color operations replace the author fill/background with one solid color; the limited contract does not expose gradient-stop editing;
- manual targets form a discriminated union, reject unknown fields and are unique within their slide record;
- translation is measured in inches relative to the layout result before manual translation; stored records are current values, not an append-only operation log.


`SlidesEditableTextContent` reuses the source `LayoutPlainTextRun` structure; it is not a frontend-only schema. `isEditableTextContent` strictly checks keys and types against that contract. Source admission continues to own normalized colors and compiler validity. The sandbox ambient declarations and Agent-facing layout references are generated from the same definitions. Manual run payload digests canonicalize style property order, so equivalent JSON key ordering does not break idempotent retries.

`functions/editableTextStyle.ts` owns whole-text field patching and mixed-value summaries without a DOM/editor dependency. For a new whole-text command, the backend first reads the original author content from the exact checked DeckSpec revision. The source writer patches each rich run and writes the resulting complete content together with the inherited node fields in one manual record. Existing v2 source semantics remain unchanged: explicit run fields take precedence over inherited node style. A later local full-value edit therefore wins naturally; old documents need no reinterpretation or migration. Text input retains a concrete baseline, while mixed toolbar values remain a separate derived summary.


## Additions, order and editing transactions

Version 2 slide records also accept `additions` and `paintOrder`. Additions are strict discriminated author values: Text with complete text-only runs/style, solid rectangle/ellipse with complete text-only content, or an image referencing a document-owned immutable asset ID with contain/cover fit. Each addition has a unique editKey and absolute box in inches. The compiler appends ordinary author nodes before identity validation and Yoga; existing target overrides then apply normally. Source tracing maps additions back to their literal locations, never to generated renderer IDs.

Text additions may declare `heightMode: 'content' | 'minimum'`. New UI text uses `content`: box.h is the initial placement/placeholder height, and the compiled height follows text content. Copies explicitly use `minimum` to retain their captured height. Omitted heightMode retains the existing minimum-height meaning for saved additions; the compiler never guesses whether an old object was inserted or copied. Source-authored Text height/minHeight constraints keep their own semantics.

`paintOrder` changes paint order among keyed siblings after layout; it never reparents or moves a Flex child. Unkeyed siblings retain their slots. `set_layer` exposes front/back/one-step-forward/one-step-backward. `move_slide` rewrites a proven static compose list; declaration/source ownership order is independent of display order.

`batch` is an atomic list of 1–1000 object operations with no nesting or page operations. Operations apply in order against the same base revision, so one target may receive several edits (for example a move followed by a width change); a target cannot be edited after it is deleted in the same batch, and an ancestor cannot appear together with its descendant. `undo`/`redo` carry no arbitrary source or historical target; the backend selects a valid session history entry. A committed result includes the current history revision ID and undo/redo depth. An undo/redo result may also carry `focus`: the slide index in the restored revision and the edited `slideKey/editKey` refs, which may no longer exist there.

`set_text_style` additionally accepts explicit boolean bold/italic/underline and left/center/right alignment. False overrides an authored emphasis. `set_text_width` changes only the Text width before Yoga; it preserves the authored height and text overflow policy. `set_image` references an already document-owned asset and/or contain/cover fit, preserving geometry; it accepts neither arbitrary paths nor URLs. New additions may preserve Shape rich content during copy, while Shape inline text editing remains plain-string-only.

Image adoption returns the strict `SlidesImportedImage` DTO (owned asset ID and positive integer pixel width/height). Renderer parses it before using the dimensions; file bytes and local preview sources are not part of this response or any manual-edit command. Ownership and asset reachability remain backend responsibilities.

## System identity lifecycle

The sandbox [authoring identity owner](../../backend/sandbox/authoringIdentity/README.md) defines system source markers, unique call paths and revision-bound loop identities. The persisted v2 shape and explicit-key semantics remain unchanged. Current-revision references stay identical through the first marker write and subsequent manual saves. Missing targets are retained but suspended during source compilation; malformed values and invalid new commands remain errors. Source changes never rebind records by content, geometry or occurrence count.
