# 开源 AI 产品的网页搜索与网页抓取能力调研

**调研时间：2026 年 7 月 18 日**

本次覆盖约 27 个项目或组件，包括 Hermes Agent、OpenClaw、OpenAI Codex、DeerFlow、OpenManus、AutoGPT、Vane/Perplexica、Morphic、MindSearch、GPT Researcher、LangChain Open Deep Research、OpenDeepSearch、Jina Reader、SearXNG、YaCy、Firecrawl、Crawl4AI、Scrapy、Crawlee、ScrapeGraphAI、Maxun、Playwright、Browser Use、Stagehand、Skyvern、agent-browser 等。

其中：

* “Hermes”按 Nous Research 的 Hermes Agent 调研。
* “Codex”按 OpenAI Codex CLI/App Server 调研。
* “Search AI”本次检索没有唯一对应到一个公认的同名开源项目，因此按“AI 搜索产品与搜索型 Agent”这一类别处理。

---

## 一、核心结论

你现在的问题不是缺少一个“更便宜的搜索 API”，而是缺少一套完整的 **Web Context Platform**。

成熟方案一般把网页能力拆成四个独立系统：

| 能力                 | 解决的问题          | 典型产物               |
| ------------------ | -------------- | ------------------ |
| Search / Discovery | 去哪里找信息         | URL、标题、摘要、排序分数     |
| Fetch / Extract    | 读取一个已知 URL     | 正文、Markdown、表格、元数据 |
| Crawl / Index      | 批量、持续、增量抓取     | 自有语料库和搜索索引         |
| Browser / Action   | 执行 JS、点击、登录、翻页 | 页面状态、交互结果、结构化数据    |

**不要用浏览器解决普通网页抓取，不要用付费抓取 API 读取所有 URL，也不要把 SearXNG 当作完整搜索索引。**

最合理的默认链路是：

```text
查询缓存
  ↓
垂直数据源 / SearXNG
  ↓ 不够好
付费搜索 API
  ↓
URL 内容缓存
  ↓
本地普通 HTTP 抓取和正文抽取
  ↓ 抓取失败或页面需要 JS
本地 Playwright/Crawl4AI/Crawlee
  ↓ 仍然失败且页面价值较高
Firecrawl / Jina 等托管服务
```

这不是完全取消付费 API，而是把它们从“默认路径”降级为“高价值失败回退”。

### 最值得借鉴的四个项目

1. **OpenClaw：最值得作为生产架构基线。**
   它明确区分搜索、普通 HTTP Fetch 和浏览器；普通 Fetch 不执行 JavaScript，只有必要时才进入 Firecrawl 或浏览器层。同时返回状态码、最终 URL、抽取器、缓存、耗时、截断、正文长度等完整观测字段。([OpenClaw][1])

2. **Hermes：最值得借鉴供应商解耦和长文压缩。**
   Hermes 可以分别配置搜索和网页抽取供应商，例如用自建 SearXNG 搜索、用 Firecrawl 抽取；对于长页面，还会按内容规模选择直接返回、单次摘要、分块摘要或拒绝处理。([GitHub][2])

3. **Codex：最值得借鉴工具协议和安全边界。**
   Codex 把网页搜索表达为 `search`、`open_page`、`find_in_page` 等事件，并提供 cached、indexed、live、disabled 等不同搜索模式。它公开展示了如何把网页结果作为“不可信输入”，以及如何限制 Agent 网络访问，但它不是可直接复用的开源全球搜索或通用爬虫。([GitHub][3])

4. **MindSearch、GPT Researcher、LangChain Open Deep Research：最值得借鉴深度研究编排。**
   这些项目擅长把复杂问题拆成子问题，搜索、读取、筛选、压缩并生成带引用的报告。但这种 fan-out 模式会成倍增加搜索、抓取和模型调用，不适合作为所有用户查询的默认模式。([GitHub][4])

# 二、Agent 与 AI 搜索产品横向比较

## 1. Hermes Agent

Hermes 的核心 `web_search` / `web_extract` 当前支持 Firecrawl、Tavily、Exa、Parallel，并允许选择后端。仓库另带 DuckDuckGo 免费 fallback skill：仅在核心 Web toolset 不可用时显示，依赖另行安装的 `ddgs`，不是核心工具的默认 Provider。此前把 SearXNG、Brave、DuckDuckGo、xAI 一并写成当前核心后端不准确，现按 2026-07-19 源码更正。([GitHub][2])

### 值得借鉴

* 搜索和网页读取的供应商完全解耦。
* 可以将便宜或自建的搜索与更可靠的网页抽取组合。
* 长页面不直接全部进入主模型，而是采用分级压缩。
* 可以用便宜的辅助模型负责网页摘要，避免污染主 Agent 的 token 成本。

### 局限

* 搜索结果质量仍依赖外部搜索源。
* 长页面摘要可能丢失表格、列表、代码块和精确字段。
* 若每个页面都调用模型摘要，整体费用仍然可能很高。
* 它没有解决持续爬取、站点调度、自有索引等问题。

### 对你产品的启示

应当允许类似下面的配置：

```yaml
search:
  default: searxng
  fallback: brave

extract:
  default: local_http
  js_fallback: crawl4ai
  managed_fallback: firecrawl

compression:
  model: small_model
  max_raw_tokens: 12000
```

## 2. OpenClaw

OpenClaw 的网页系统是本次调研中最完整、最接近生产级中间层的一套设计。

它的普通 `web_fetch` 使用 HTTP GET，不执行 JavaScript；可以做正文抽取、缓存、重定向处理、正文截断，并在本地抽取失败时回退到 Firecrawl。它还提供独立的浏览器工具，使用隔离的 Chromium/Chrome profile 执行标签页、点击、表单、快照、截图、PDF 和下载操作。([OpenClaw][5])

其搜索层支持大量供应商，并将结果归一化；官方实现也包含查询缓存。([OpenClaw][1])

2026-07-19 复核时，OpenClaw 已包含三种零 Key 路径：实验性的 DuckDuckGo HTML 抓取、Parallel 的免费 Search MCP、用户自托管的 SearXNG。它们都必须显式选择，不会在没有 API Key 时自动成为默认；官方尤其说明 DuckDuckGo 不是正式 API，可能因挑战页或 HTML 变化而失效。这个设计说明“免费入口”适合改善首次使用体验，但不应被包装成生产稳定性保证。

### 最值得复制的返回字段

```json
{
  "url": "...",
  "finalUrl": "...",
  "status": 200,
  "contentType": "text/html",
  "title": "...",
  "extractor": "readability",
  "renderMode": "http",
  "cached": false,
  "truncated": false,
  "length": 18231,
  "rawLength": 92817,
  "fetchedAt": "...",
  "tookMs": 624,
  "warnings": [],
  "text": "..."
}
```

这类字段非常重要，因为你最终需要知道：

* 是搜索质量不好，还是网页没抓下来；
* 是 HTTP 抓取失败，还是正文抽取失败；
* 是否进入了浏览器；
* 是否命中了缓存；
* 成本和延迟到底发生在哪一层。

### 局限

* 它没有自己的全球网页索引。
* Readability 类正文抽取器更适合文章，对商品列表、复杂表格、仪表盘和论坛结构未必理想。
* 浏览器池、隔离 profile、下载安全和资源调度仍然需要运维。

## 3. OpenAI Codex

Codex 的公开实现重点不是自建搜索，而是定义 Agent 如何使用托管网页搜索。

其 App Server 将搜索过程建模为事件：

```text
search(query)
open_page(url)
find_in_page(url, pattern)
```

同时区分 cached、indexed、live 和 disabled 等模式。cached 模式可以减少实时访问不可信网页的次数，但结果仍然必须被当作不可信内容处理。Codex CLI 和 IDE 扩展也没有把完整浏览器自动化作为内置能力。([GitHub][3])

### 值得借鉴

* Search、Open、Find 三类动作比一个万能 `browse()` 更容易观测和控制。
* 实时搜索和缓存搜索应当是显式模式，而不是隐含行为。
* 网络权限应按任务阶段开启，而不是 Agent 永远拥有任意出网权限。
* 网页内容不能直接改变工具权限或系统指令。

### 不适合直接复制的部分

Codex 使用的是 OpenAI 托管搜索能力。其公开代码并不等于可以自建同等质量的全球搜索索引，因此它更适合作为 **工具协议、安全模型和事件模型参考**。

---

## 4. DeerFlow、OpenManus、AutoGPT

DeerFlow 提供网页搜索、网页抓取和渲染页面捕获，并支持通过 MCP 或 Python 扩展工具。它还强调追踪模型调用、工具输入输出、耗时和 token，适合作为研究 Agent 的编排和可观测性参考。([GitHub][6])

OpenManus 更多是一个工具集成框架，浏览器能力主要来自 Playwright、Browser Use 和 Crawl4AI，而不是其自身独特的搜索或爬虫系统。([GitHub][7])

AutoGPT 较早就把 Web Search 和 Selenium 浏览器拆成不同组件，这种职责分离是正确的；不过当前 AutoGPT Platform 的部分代码采用 Polyform Shield，而非全部 MIT，做商业托管产品时需要单独核查许可证。([GitHub][8])

---

## 5. Vane、Morphic：AI 搜索产品层

Vane，即原 Perplexica，是一个自托管 AI 搜索产品，使用 SearXNG 进行搜索，并提供不同搜索质量模式、来源聚焦、引用展示和本地模型支持。([GitHub][9])

Morphic 同样面向带引用的 AI 搜索体验，支持 Tavily、SearXNG、Brave、Exa 等不同搜索后端，并提供 Quick、Adaptive 等搜索模式。([GitHub][10])

### 适合借鉴

* 搜索模式：快速回答、平衡模式、深度模式。
* 来源类型过滤：网页、学术、讨论区、代码、新闻。
* 引用和搜索过程的前端展示。
* 搜索供应商抽象层。
* 用户可以显式选择成本和质量。

### 不应误解

Vane 和 Morphic 主要是 **搜索产品和回答体验**，不是高质量通用爬虫。接入 SearXNG 可以减少搜索 API 调用，但不能自动解决 JS 页面、反爬、正文抽取、表格和 PDF 等抓取问题。

---

## 6. MindSearch、GPT Researcher、Open Deep Research

这类项目采用的是：

```text
复杂问题
  → 问题拆分
  → 多路搜索
  → 多页面读取
  → 内容过滤与压缩
  → 补充搜索
  → 综合报告
```

GPT Researcher 会先生成研究问题，再调用多个爬取 Agent 收集、过滤和汇总来源。LangChain Open Deep Research 则把研究、摘要、内容压缩和最终报告配置为不同模型或不同阶段。([GitHub][11])

### 正确使用方式

将其设计成显式的“深度研究”模式，并设置硬预算，例如：

```yaml
deep_research:
  max_subqueries: 8
  max_search_calls: 12
  max_documents: 20
  max_browser_pages: 4
  max_total_tokens: 120000
  deadline_seconds: 180
```

不要让所有普通问答都默认进入多 Agent 研究流程。

---

## 7. OpenDeepSearch 与 Jina Reader

OpenDeepSearch 将搜索、网页读取和语义重排封装成适合 Agent 使用的搜索工具，并提供普通和更深入的搜索模式。([GitHub][12])

Jina Reader 提供 URL 到 LLM 友好文本的读取方式，并可根据网页情况选择普通请求或无头浏览器；它还能处理 PDF、Office 文档和图片。Jina DeepResearch 则在搜索、阅读和推理之间循环，直到得到答案或达到预算。([GitHub][13])

Jina 很适合作为托管 fallback，但如果把“搜索”和“读取前几个结果”完全绑定，成本控制和网页选择会不如自建的分层系统精细。

# 三、搜索基础设施

## SearXNG

SearXNG 是自托管元搜索引擎，通过适配器聚合大量第三方搜索服务，并提供 JSON、CSV、RSS 等输出格式。官方文档当前列出可聚合多达 279 个搜索服务。([SearXNG 文档][14])

### 优点

* 自建后单次查询没有 SaaS API 费用。
* 可以组合多个搜索来源。
* 可以按语言、时间、类别和引擎配置。
* 对 Vane、Morphic、Hermes 等 Agent/搜索产品已有成熟集成。

### 关键限制

**SearXNG 不是自己的全球网页索引。**

它仍然请求外部搜索引擎，因此会继承：

* 上游限流和封禁；
* 不同引擎响应速度差异；
* 代理和出口 IP 质量问题；
* 部分引擎结果不稳定；
* 公共 SearXNG 实例可能关闭 JSON 输出。

官方文档也明确提供超时、代理、重试等配置，因为上游引擎可能超时或阻断请求。([SearXNG 文档][15])

### 推荐定位

把 SearXNG 当作：

```text
低成本、高覆盖的第一层候选结果生成器
```

而不是：

```text
可以完全替代 Google、Bing、Brave、Exa 的高质量搜索索引
```

建议给每个 SearXNG 上游引擎维护动态健康分：

```text
health_score =
  success_rate
  × freshness_score
  × result_quality
  ÷ p95_latency
```

连续超时或返回低质量结果的引擎应临时熔断。

---

## YaCy

YaCy 与 SearXNG 不同，它具有自己的索引、爬虫和调度系统，也可以用于内网和受控语料库。([GitHub][16])

但自建一个覆盖公开互联网、更新及时且排序良好的综合搜索索引，需要极高的抓取、存储、去重、垃圾检测和排名投入。YaCy 更适合：

* 企业内网；
* 固定站点集合；
* 行业语料库；
* 已知域名的专题搜索；
* 离线或隐私优先场景。

不建议把它作为通用全球搜索 API 的直接替代品。

# 四、网页抓取与爬虫项目比较

| 项目            | 最适合的用途                                  | 不适合的用途             |
| ------------- | --------------------------------------- | ------------------ |
| Firecrawl     | 托管抓取、crawl、map、截图、JSON 抽取、困难页面 fallback | 所有 URL 的默认低成本抓取    |
| Crawl4AI      | Python、本地 JS 渲染、AI 友好正文、批量浏览器抓取         | 搜索索引、超大规模纯 HTTP 爬虫 |
| Scrapy        | 持续爬取、队列、调度、增量任务、站点级采集                   | 默认执行 JS 的动态网页      |
| Crawlee       | TypeScript 中统一 HTTP 与 Playwright 爬虫     | Python 主技术栈中的直接嵌入  |
| ScrapeGraphAI | LLM 驱动的定制结构抽取                           | 每个页面的默认正文读取        |
| Maxun         | 录制并重复执行的结构化抓取、监控和 API 化                 | 一次性开放式研究搜索         |

## Firecrawl

Firecrawl 提供 scrape、crawl、map、search、截图、结构化 JSON 和浏览器交互等较完整能力，并支持自托管；其开源项目采用 AGPL-3.0。([GitHub][17])

它适合保留为：

* 403、429 或反爬页面的高价值回退；
* 复杂 JavaScript 页面；
* 临时需要截图或结构化 JSON 的任务；
* 自建浏览器池故障时的容灾方案。

不建议所有结果都直接调用 Firecrawl，因为你会再次形成昂贵的单点依赖。

---

## Crawl4AI

Crawl4AI 是 Python 生态中最适合作为 Agent 网页渲染层的项目之一。它默认可使用 Playwright，支持浏览器池、JavaScript 执行、HTML、Markdown、截图、PDF 和 MCP 等能力，采用 Apache-2.0。([GitHub][18])

推荐放在普通 HTTP 抓取之后：

```text
HTTP GET
  → 内容质量合格：返回
  → 检测到 JS Shell / 空正文：Crawl4AI
```

不要因为 Crawl4AI 易用，就让所有静态网页都启动浏览器。浏览器的 CPU、内存、启动和页面加载成本远高于普通 HTTP。

---

## Scrapy

Scrapy 是成熟的异步爬虫框架，包含 Engine、Scheduler、Downloader、中间件、Spider 和 Item Pipeline，可暂停、恢复任务，并适合大规模、持续性采集。([Scrapy][19])

它最适合建立单独的“长期语料采集通道”：

* 高频访问网站；
* 官方文档；
* 博客和新闻源；
* 开源项目文档；
* 固定行业站点；
* Sitemap 和 RSS；
* 定期更新检测。

Scrapy 不应替代 Playwright，而应负责绝大多数确定性的 HTTP 采集。

---

## Crawlee

Crawlee 同时提供基于普通 HTTP 的 CheerioCrawler 和基于浏览器的 PlaywrightCrawler，并尽量保持相似的编程接口，因此很适合在 TypeScript 技术栈中实现 HTTP 到浏览器的自动升级。([Crawlee][20])

推荐结构：

```typescript
try {
  return await cheerioCrawler.fetch(url);
} catch (error) {
  return await playwrightCrawler.fetch(url);
}
```

实际实现中不应只根据异常升级，还要根据抽取后的正文质量、页面特征和业务价值决定。

---

## ScrapeGraphAI

ScrapeGraphAI 使用 LLM 和图式工作流抽取网页信息，支持 Playwright 和多页面搜索流程，采用 MIT 许可证。其开源部署仍需自行承担模型 token、浏览器、代理和反爬成本。([GitHub][21])

正确定位是：

```text
确定性 DOM/JSON-LD/表格抽取失败
  → 页面价值较高
  → 调用 LLM 进行定制字段抽取
```

不应将 LLM 抽取作为普通文章正文读取的默认方式。

---

## Maxun

Maxun 侧重无代码网页抓取、爬取、搜索、AI 抽取，以及把网站转成结构化 API。它更适合“录制一次、重复运行”的固定任务。([GitHub][22])

例如：

* 每天读取固定后台表格；
* 监控商品或页面字段变化；
* 将某个站点封装为内部 API；
* 固定分页和点击流程。

它不是通用 Agent 临时搜索和读取任意网页的首选底层。

# 五、浏览器 Agent 比较

## Playwright：基础执行层

Playwright 的 BrowserContext 可以提供相互隔离的浏览器会话，适合多租户或多任务并行。其认证状态文件可能包含敏感 Cookie 和请求头，因此不能跨用户复用或不加密存储。([Playwright][23])

Playwright 应当是基础设施，而不是直接暴露给主 Agent 的无限权限工具。

## Stagehand：确定性代码与 AI 的折中

Stagehand 的核心思路是：

* 已知页面和流程使用代码；
* 未知或变化页面使用自然语言和 AI；
* 支持 `act`、`extract`、`agent`；
* 支持缓存和一定程度的自恢复。

这比所有操作都交给视觉模型更符合生产系统的成本和稳定性要求。([GitHub][24])

## agent-browser：适合编码 Agent

agent-browser 提供 Rust CLI 和可访问性树快照，通过稳定的元素引用执行点击、填写和读取，采用 Apache-2.0。([GitHub][25])

它的优势是给模型的页面表示比完整 DOM 或截图更小，适合：

* Coding Agent；
* 命令行 Agent；
* 低 token 浏览器控制；
* 可记录、可重放操作。

## Browser Use

Browser Use 适合开放式的一次性浏览任务，如点击、填表、读取和问答，采用 MIT 许可证。([GitHub][26])

它的弱点不是能力不足，而是当任务能用普通 HTTP 或固定 Playwright 脚本完成时，开放式 Agent 浏览器通常更慢、更贵、也更难复现。

## Skyvern

Skyvern 使用 Playwright 兼容的浏览器执行层，并结合 LLM 和视觉完成工作流自动化，采用 AGPL。它更偏向业务流程自动化，而不是普通网页正文抓取。([GitHub][27])

# 七、搜索路由设计

不同查询应该走不同来源。

| 查询类型    | 默认策略                      |
| ------- | ------------------------- |
| 导航型、官网型 | SearXNG + 域名/标题匹配         |
| 编程和项目文档 | GitHub、官方文档、站内 Sitemap 优先 |
| 学术查询    | 学术数据源优先，再补普通网页            |
| 最新新闻和事件 | RSS、官方发布源和具备时间过滤的搜索源      |
| 语义探索    | Exa 或类似语义搜索作为付费 fallback  |
| 普通事实问题  | SearXNG + 本地抓取            |
| 多跳研究    | 显式进入 Deep Research 模式     |

不要固定每次调用两三个搜索 API。采用并行与回退相结合的策略：

```python
results = query_cache.get(query)

if not results:
    results = vertical_search(query)

if results_quality(results) < threshold:
    results += searxng_search(query)

if results_quality(results) < threshold:
    results += paid_search(query)

results = normalize_dedupe_rank(results)
```

### 搜索质量不应只看“有没有结果”

建议计算：

```text
search_quality =
    official_source_rate
  + title_query_relevance
  + snippet_answerability
  + freshness
  + domain_diversity
  - duplicate_rate
  - spam_rate
```

# 八、抓取升级策略

## 第 0 层：缓存与 URL 规范化

在访问页面前：

* 去除常见跟踪参数；
* 处理 canonical URL；
* 合并 HTTP/HTTPS 和尾部斜杠变体；
* 根据内容新鲜度设置不同 TTL；
* 使用内容哈希做跨 URL 去重；
* 支持 ETag 和 Last-Modified 条件请求。

文章、文档和历史页面可以缓存较久；新闻首页和实时数据应缓存更短。

## 第 1 层：普通 HTTP

默认只使用普通 HTTP：

* 严格超时；
* 最大响应体限制；
* 最大重定向次数；
* MIME 类型识别；
* gzip/br 解压；
* HTML 正文抽取；
* JSON-LD、OpenGraph 和 meta 提取；
* PDF、JSON、XML、CSV 分流处理。

## 第 2 层：质量判断

HTTP 状态为 200 并不代表抓取成功。可以检测：

```text
正文长度过短
正文与 HTML 比例过低
只有 “Enable JavaScript”
只有 SPA root 节点
页面主体大量是脚本
标题存在但正文为空
正文高度重复导航菜单
需要展开、滚动或点击
403 / 429 / challenge 页面
```

输出明确的失败原因：

```text
dns_error
timeout
http_403
http_429
server_error
captcha
login_required
js_required
empty_content
unsupported_mime
too_large
robots_block
policy_block
ssrf_block
```

## 第 3 层：本地浏览器渲染

只有符合以下条件才升级：

```text
页面价值高
AND 普通 HTTP 抽取失败
AND 预计浏览器能解决
AND 尚未超过本次请求预算
```

不要对明显的登录墙、付费墙或强 CAPTCHA 页面无休止重试。

## 第 4 层：托管抓取 fallback

只有高价值页面进入 Firecrawl、Jina 或现有 Fetch API：

```text
paid_fetch =
  local_http_failed
  AND local_browser_failed
  AND page_utility >= threshold
```

页面价值可以近似计算为：

```text
utility =
  search_relevance
  × source_trust
  × novelty
  × estimated_answerability
  ÷ estimated_fetch_cost
```

# 九、不要固定抓取 Top 10

常见的浪费模式是：

```text
搜索 10 条结果
→ 抓取全部 10 页
→ 全部送入模型
```

更好的方式是渐进式证据采集：

```text
先抓 Top 3
  ↓
判断是否已回答主要问题、是否有足够独立来源
  ↓ 不足
再抓 2～3 个来源
  ↓
必要时生成补充查询
```

停止条件可以包括：

* 已有两个或三个相互独立的可靠来源；
* 关键结论都有直接证据；
* 新页面的新增信息量持续下降；
* 达到费用、token 或时间预算；
* 发现来源之间存在矛盾，需要专门验证。

这通常比更换搜索供应商更能降低总成本。

# 十一、成本模型

假设你的产品每月有 10 万次需要联网的用户请求。

当前方案假设：

```text
每次请求 2 次付费搜索
每次请求抓取 5 个页面
```

则每月：

```text
付费搜索调用：100,000 × 2 = 200,000
付费抓取调用：100,000 × 5 = 500,000
```

采用分层架构后，做一个示例测算。

## 搜索

假设：

* 查询缓存命中率 25%；
* 剩余请求中，SearXNG 或垂直数据源能满足 70%；
* 其余请求调用一次付费搜索。

```text
100,000 × 75% × 30%
= 22,500 次付费搜索
```

与 200,000 次相比，付费搜索调用减少约 **88.75%**。

## 抓取

假设：

* URL 内容缓存命中率 35%；
* 剩余页面中，本地 HTTP 成功率 78%；
* 浏览器解决剩余失败页面的 70%；
* 最后才调用付费抓取。

```text
500,000
× 65%
× 22%
× 30%
= 21,450 次付费抓取
```

与 500,000 次相比，付费抓取调用减少约 **95.71%**。

这只是说明分层模型的量级，不是效果承诺。实际结果取决于：

* 用户查询重复率；
* URL 重复率；
* 页面是否高度动态；
* 新闻和实时信息占比；
* 反爬站点占比；
* 浏览器、代理和模型 token 的自建成本。

付费 API 调用下降 95%，不等于总成本下降 95%；你会新增服务器、浏览器池、代理、缓存和运维费用。但自建部分通常可预测性更高，且能获得完整可观测性。

不要直接根据 GitHub Star 或供应商公开 benchmark 选型。建立自己的评测集。

| 中文和英文长尾问题      |  100 |
| 学术或专业问题        |   50 |
| 多跳和深度研究        |   50 |
| 易受 SEO 垃圾影响的问题 |   50 |

## URL 抓取集

至少包含：

* 静态文章；
* 产品和列表页；
* 官方文档；
* 论坛；
* SPA；
* 无限滚动；
* PDF；
* 表格；
* iframe；
* 登录墙；
* 付费墙；
* 403、429 和 CAPTCHA；
* 中英文混排；
* 极长页面；
* 重定向和短链接。

## 对比组

```text
A. 当前搜索 API + 当前 Fetch API
B. SearXNG + 当前 Fetch API

D. C + 浏览器自动升级
```

## 指标

### 搜索

* Recall@5、Recall@10；
* NDCG@10；
* 官方来源比例；
* 新鲜度错误率；
* 重复域名比例；
* 垃圾和低可信来源比例；
* 无有效结果率。

### 抓取

* HTTP 成功率；
* 正文抽取成功率；
* JS 页面恢复率；
* 表格、列表和代码块保留率；
* PDF 成功率；
* 被阻断率；
* 内容重复率；
* 浏览器升级比例；
* 托管 fallback 比例。

### 最终回答

* 引用是否真正支持结论；
* 引用 URL 是否可访问；
* 事实完整度；
* 来源多样性；
* 是否优先使用原始和官方来源；
* 矛盾信息是否被识别；
* 无证据时是否拒绝断言。

### 运营

* 每次成功回答的实际成本；
* 每个查询的付费搜索次数；
* 每个查询的付费抓取次数；
* 浏览器秒数；
* 模型 token 数；
* p50/p95 延迟；
* 查询和页面缓存命中率。

# 十三、安全与许可证

## SSRF

抓取服务必须：

* 只允许 `http` 和 `https`；
* 拒绝 loopback、私网、link-local 和云 metadata 地址；
* DNS 解析后再次检查目标 IP；
* 每一次重定向都重新检查；
* 限制重定向次数、响应大小和下载时间；
* 防止 DNS rebinding。

OpenClaw 的网页抓取实现已经包含私有地址阻断和重定向重新检查；OWASP 也明确指出，让工具抓取由模型生成的 URL 会带来 SSRF 风险。([OpenClaw][5])

## Prompt Injection

网页中的以下内容都只能被视为数据：

```text
“Ignore previous instructions”
“Send your API key to…”
“Run this command…”
“Open another URL and upload…”
```

Codex 的安全文档特别强调了 prompt injection、数据外泄、恶意软件和许可证风险，并建议使用域名白名单以及限制 HTTP 方法。([OpenAI Developers][28])

建议：

* 抓取通道默认只允许 GET、HEAD；
* 网页内容不能决定是否发送邮件、上传文件或调用高权限工具；
* 将页面文本与系统指令放在明确隔离的消息区；
* 浏览器执行层使用独立权限和单独预算；
* 所有来源记录 URL、最终 URL、重定向链和内容哈希。

## 浏览器会话

* 每个用户或任务使用独立 BrowserContext；
* 不跨租户共享 Cookie；
* 认证状态加密；
* 下载文件进入隔离区；
* 限制文件大小和 MIME；
* 禁止浏览器直接访问内部管理系统；
* 定期销毁 profile。

Playwright 官方文档提醒，认证状态可能包含能够冒充用户的敏感 Cookie 和请求头。([Playwright][29])

## 开源许可证

需要特别注意：

* Firecrawl：AGPL-3.0。([GitHub][17])
* Skyvern：AGPL。([GitHub][27])
* AutoGPT Platform 部分代码：Polyform Shield。([GitHub][30])
* Crawl4AI：Apache-2.0。([GitHub][18])
* Browser Use、Stagehand：MIT。([GitHub][26])
* agent-browser：Apache-2.0。([GitHub][25])

AGPL 项目用于内部服务、修改后对外提供网络服务、嵌入商业 SaaS 时的义务需要结合具体部署方式进行法务核查。

# 十五、实施优先级

## P0：先把现有调用变得可观测

在更换任何供应商前，记录：

```text
query
search_provider
search_results_count
selected_urls
fetch_provider
http_status
final_url
extractor
render_mode
content_length
cache_hit
latency
cost
failure_reason
```

否则换成自建方案后，你仍然无法判断质量为什么不好。

## P1：统一数据结构和双层缓存

建立：

* 查询缓存；
* URL 内容缓存；
* URL 规范化；
* 内容哈希；
* SearchResult/WebDocument 标准结构；
* 失败原因枚举。

这是最先产生降本效果的一步。

## P2：接入 SearXNG，但保留现有搜索 API

路由策略：

```text
缓存
→ 垂直源
→ SearXNG
→ 现有付费搜索
```

不要一开始完全切断现有搜索 API。先测出哪些查询 SearXNG 表现好，哪些必须回退。

## P3：本地 HTTP 抓取替换大部分 Fetch API

优先覆盖：

* 新闻文章；
* 博客；
* 官方文档；
* GitHub 页面；
* 普通 HTML；
* PDF；
* RSS、XML 和 JSON。

这是最可能产生最大费用下降的阶段。

## P4：增加 JS 检测和浏览器升级

引入 Crawl4AI、Crawlee 或 Playwright，但设置：

* 最大并发；
* 单页超时；
* 单任务浏览器页面数；
* 每次查询最多浏览器升级数；
* 单域名速率；
* 内存和 CPU 预算。

## P5：建立持续爬取和自有语料

对产品中反复出现的来源，不应每次实时搜索和抓取。

使用 Scrapy 或 Crawlee 做：

```text
Sitemap/RSS 发现
→ 增量抓取
→ 内容去重
→ 变化检测
→ 自有索引
```

随着高频内容进入自有语料，搜索 API 和实时抓取调用会继续下降。

## P6：最后增加 Deep Research

借鉴 MindSearch、GPT Researcher 和 LangChain Open Deep Research，但只作为显式高级模式，并给每次任务设置查询数、URL 数、浏览器数、token 和费用上限。

---

# 最终建议

你的第一版增强方案不需要直接部署一个庞大的“开源 Perplexity”。

最合理的组合是：

```text
OpenClaw 的分层架构和观测字段
+ Hermes 的搜索/抽取供应商解耦
+ Codex 的 search/open/find 工具协议与安全边界
+ SearXNG 的低成本候选结果
+ 本地普通 HTTP 正文抽取
+ Crawl4AI 或 Crawlee 的 JS 自动升级
+ Scrapy/Crawlee 的持续爬取
+ Firecrawl 或 Jina 作为困难页面 fallback
+ MindSearch/Open Deep Research 的显式研究模式
+ Vane/Morphic 的搜索产品体验
```

优先级最高的不是再增加更多 API，而是实现以下三个组件：

1. **统一的 Search Router**：缓存、垂直源、SearXNG、付费 fallback。
2. **统一的 URL Context Service**：HTTP、正文抽取、浏览器升级、托管回退。
3. **完整的质量与成本观测系统**：知道每一次搜索和抓取为什么成功、为什么失败、花了多少钱。

做到这三点后，你现有的搜索和 Fetch API 不需要删除，而会从昂贵的默认基础设施变成少量、高价值、可替换的兜底能力。
