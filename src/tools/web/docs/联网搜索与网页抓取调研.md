## 2. 先统一四个概念

这些能力经常被统称为“联网”，但实现、成本和风险完全不同：

| 能力 | 输入 | 输出 | 典型用途 |
| --- | --- | --- | --- |
| 搜索（search） | 查询词 | 标题、URL、摘要、排名 | 找候选资料 |
| 单页读取/抽取（read/extract/scrape） | 一个或少量 URL | 清洗后的正文、标题、元数据 | 阅读和引用原文 |
| 站点爬取（crawl） | 起始 URL + 范围/预算 | 多页面集合及关系 | 文档站、专题站批量采集 |
| 浏览器自动化（browser） | URL + 交互动作 | 渲染后 DOM、截图、操作结果 | JS 页面、登录、点击、表单 |

Linnya 不应把四者合并为一个万能工具。搜索与读取是常规研究能力；爬取是有预算、并发、取消和进度的长流程；浏览器自动化具有会话生命周期和更高安全风险，应该是独立业务边界。

## 3. 结论摘要

1. **Hermes 的核心联网搜索并不是无条件免费。** `web_search` / `web_extract` 只有在 Exa、Parallel、Tavily、Firecrawl 之一可用时才会暴露给模型。可用性来自用户 API Key、Firecrawl 自托管地址，或付费 Nous 订阅的 Tool Gateway。Hermes 源码明确排除了 Nous 免费层的 Tool Gateway 权限。
2. **Hermes 另带一个免费的 DuckDuckGo fallback skill，但它不等于核心 `web_search` 默认免费。** 该 skill 仅在 `web` toolset 不可用时显示，依赖用户另行安装 `ddgs` CLI/Python 包，返回搜索摘要而非正文，并明确记录限流、云 IP 封禁和空结果风险。它适合零 Key 备用入口，不是 Hermes 对生产可用率的承诺。
3. **Hermes 有 `web_crawl_tool` 实现，但当前没有注册成模型工具。** 注册表只注册了 `web_search` 和 `web_extract`，核心 toolset 也只包含这两个。不能把模块中存在的函数等同于用户已经具备站点爬取能力。
4. **新版 Codex 有两套服务端搜索路径。** 一套是 Responses API 原生 `web_search`；另一套是独立 `web.run` 扩展，调用 `/v1/alpha/search`，支持搜索、打开引用、页内查找、截图以及结构化结果回传。两者都不是本地搜索引擎，成本和权限归属于 OpenAI 服务/账号。
5. **新版 Codex 确实可以操作浏览器进行搜索。** Browser 插件可控制内置浏览器或 Chrome，支持标签页、导航、DOM snapshot、受限 Playwright、坐标/DOM CUA、截图、下载和 CDP。它可以打开搜索引擎、输入查询、查看结果并点击页面，但这是浏览器自动化，不是 `web_search` 的实现。
6. **浏览器搜索不适合作为 Linnya 默认搜索后端。** 它适合用户明确要求操作网页、复用登录态、访问 JS 页面或验证 UI；常规资料发现仍应优先用结构化搜索 API，否则会承受 DOM 漂移、验证码、速率限制、延迟和证据归一化成本。
7. **Linnya 已有可用基础，不应重做。** 当前已有 `web_search`、`web_read`、Provider 工厂、`[@ref]` 引用、EvidenceStore、会话投影和编辑器引用水合。缺口主要是安全策略、超时与预算、站点爬取、动态页面和清晰的跨 domain 边界。
8. **OpenClaw 确实提供零 Key 搜索，但官方也不把它们自动选为默认。** DuckDuckGo 是抓取非 JavaScript HTML 页面的非官方实验性实现；Parallel Free 走官方免费 Search MCP；SearXNG 需要自托管。OpenClaw 的自动检测只选择已配置凭证的 Provider，零 Key Provider 必须由用户显式选择。
9. **Linnya 可以把“零配置免费搜索”做成首次使用默认，但不能把“免费”写成“稳定保证”。** 默认候选应优先评估有正式服务合同的 Parallel Free；DuckDuckGo 作为明确标注实验性的可选项；SearXNG 仅接受用户自托管地址。百度千帆与 Serper 保留为可配置的稳定选项，不做静默跨 Provider 兜底。

### 3.1 OpenClaw 的零 Key 搜索边界

OpenClaw 当前统一的 `web_search` 支持多种 Provider，其中与“免费默认”直接相关的有三类：

| Provider | 是否需要 Key | 实际依赖 | 官方定位 | 适合作为 Linnya 默认吗 |
| --- | --- | --- | --- | --- |
| Parallel Free | 否 | Parallel 托管的免费 Search MCP | 显式选择、非自动检测 | **默认候选，需小规模 live 验证** |
| DuckDuckGo | 否 | 抓取 DuckDuckGo 非 JavaScript HTML 搜索页 | 实验性、非官方、可能遇到挑战页或 HTML 变化 | 适合实验性可选，不宜承担 95% 可用率 |
| SearXNG | 否 | 用户自己的 SearXNG 实例及其上游搜索引擎 | 自托管元搜索 | 适合高级用户配置，不适合桌面端零配置默认 |

OpenClaw 还明确规定：零 Key Provider 不参与自动检测，必须在设置中显式选择。这个边界值得保留，因为“客户端代码开源”“调用时不填 Key”“服务长期免费”“搜索链路稳定”是四件不同的事。Parallel Free 仍依赖第三方托管服务；DuckDuckGo 没有正式 API 合同；SearXNG 虽然真正开源，但部署和上游健康度由用户承担。

对 Linnya 的直接启示是：产品可以默认选中一个零 Key Provider，让新用户开箱可搜；运行时只执行用户当前选中的单一 Provider。连接失败时给出可理解错误和设置入口，不暗中改用可能产生费用或改变隐私边界的另一家 Provider。

## 4. Hermes Agent 实现分析

### 4.1 模型看到工具的调用链

调用链如下：

```text
toolsets.py
  -> model_tools.get_tool_definitions()
  -> registry.get_definitions()
  -> check_web_api_key() 过滤不可用工具
  -> web_search / web_extract schema 暴露给模型
  -> registry handler
  -> tools/web_tools.py
  -> Exa / Parallel / Tavily / Firecrawl
```

`toolsets.py` 虽然把 `web_search`、`web_extract` 放进核心工具列表，但 `registry.get_definitions()` 会执行 `check_fn`。没有任何可用后端时，这两个工具不会出现在模型工具列表中。Hermes 还会动态移除其他工具描述中对不可用 Web 工具的引用，避免模型调用不存在的工具。这一点值得 Linnya 保留：**模型可见的能力必须与运行时真实可用能力一致。**

### 4.2 Provider 选择与费用来源

Hermes 支持四类 Web Provider：

| Provider | 搜索 | 单页抽取 | 站点爬取 | 使用条件 |
| --- | --- | --- | --- | --- |
| Firecrawl | 是 | 是 | 是 | API Key、自托管 URL，或付费 Nous Tool Gateway |
| Tavily | 是 | 是 | 是 | API Key；Hermes UI 标记有免费层 |
| Exa | 是 | 是 | 否 | API Key |
| Parallel | 是 | 是 | 否 | API Key |

选择顺序是：优先读取 `config.yaml` 的 `web.backend`；未显式配置时，按 Firecrawl、Parallel、Tavily、Exa 的顺序选择第一个已配置后端。这是启动时的配置解析，不是请求失败后的自动容灾。

Firecrawl 有三种接入方式：

- 直接云 API：`FIRECRAWL_API_KEY`。
- 自托管：`FIRECRAWL_API_URL`。
- Nous Tool Gateway：使用 Nous OAuth token 访问 `firecrawl-gateway.<domain>`。

Nous Gateway 不属于免费层。`managed_nous_tools_enabled()` 明确要求已登录且不是 free tier，v0.10.0 发布说明也写明该能力面向付费 Nous Portal 订阅，并由订阅承担调用成本。

因此，对“是否免费”的准确回答是：

- Hermes 项目代码本身可以免费使用，不等于搜索数据源免费。
- Hermes 的 DuckDuckGo skill 不需要 API Key，但依赖 `ddgs` 第三方客户端和 DuckDuckGo 非正式搜索接口；它是 fallback skill，不是核心 `web_search` Provider。
- Tavily 免费层适合开发验证，不能在未核实额度、并发和商用条款时作为正式容量承诺。
- Firecrawl 自托管能减少云 API 费用，但会产生基础设施、代理 IP、反爬、存储和维护成本。
- 本地浏览器不产生云浏览器调用费，但会消耗用户机器资源，也不能自动解决验证码、登录限制和站点封禁。

### 4.3 搜索、抽取与爬取行为

`web_search` 默认只返回 5 条结果的标题、URL、摘要和位置，不抓完整正文。

`web_extract`：

- 一次最多 5 个 URL。
- 根据所选 Provider 获取正文。
- 对 URL 做私网/本地地址检查，并支持用户站点 blocklist。
- 短页面返回正文；长页面可调用辅助模型压缩到约 5,000 字符。
- 超过约 2 MB 的内容拒绝进入辅助模型处理。
- Firecrawl 调用有单 URL 超时，并在抽取后再次检查最终 URL 的站点策略。

`web_crawl_tool`：

- Tavily 和 Firecrawl 路径默认限制约 20 个页面。
- 支持逐页策略检查、正文清理和并行 LLM 压缩。
- 但当前文件末尾只有 `web_search`、`web_extract` 两个 `registry.register()`，所以普通 Agent 无法直接调用该爬取函数。

### 4.4 浏览器能力

Hermes 的浏览器工具与 Web 搜索工具分开：

- 默认 `local` 模式通过 `agent-browser` 启动本地 headless Chromium。
- 云端可选择 Browser Use、Browserbase 或 Firecrawl。
- 浏览器工具负责 navigate、snapshot、click、type、scroll、console、CDP 等交互。
- 工具描述要求简单资料获取优先使用 `web_search` / `web_extract`，只有需要交互或动态内容时才使用浏览器。

这种“便宜的搜索/抽取优先，浏览器按需启用”的分层值得 Linnya采用，但不要照搬其云失败后自动切本地浏览器的逻辑。Linnya 应让一次任务明确选择运行方式，避免云端与本地网络身份、登录态和审计语义发生变化。

### 4.5 可借鉴点与不应照搬点

可借鉴：

- Provider 统一合同与配置选择。
- 工具可用性检查后再向模型暴露 schema。
- 搜索只返回候选，正文读取按 URL 单独执行，控制 token 成本。
- URL 私网地址检查、站点 blocklist、页面数量和正文大小预算。
- 搜索/抽取与浏览器自动化分层。

不应照搬：

- `tools/web_tools.py` 超过 2,000 行，同时承担 Provider、配置、URL 策略、正文压缩、调试和流程编排，职责过多。
- 同一模块同时返回成功 JSON、错误 JSON，且部分异常被转换成普通结果；这与 Linnya 的工具错误协议不一致。
- 站点策略配置异常默认 fail-open，不适合企业管理策略。
- `web_crawl_tool` 已实现但未注册，代码存在不等于产品能力可用，容易造成文档和真实能力漂移。
- 抽取阶段内嵌 LLM 摘要，使“获取事实”和“解释事实”混在同一步，缓存、审计和成本归因更困难。

## 5. Codex 实现分析

### 5.1 两套 Web Search 路径

新版 Codex 同时保留两套搜索执行方式。

第一套是 Responses API 托管工具：

```text
WebSearchMode / WebSearchToolConfig
  -> create_web_search_tool()
  -> ToolSpec::WebSearch { type: "web_search" }
  -> OpenAI Responses API
  -> web_search_call 流事件
  -> WebSearchItem / UI
```

本地负责声明工具、发送配置、解析 `search` / `open_page` / `find_in_page` action 和投影事件，实际搜索与页面访问在服务端完成。

第二套是独立 Web Search 扩展：

```text
Feature::StandaloneWebSearch
  -> ext/web-search 注册 namespace web.run
  -> 模型调用 web.run(commands)
  -> Codex SearchClient 请求 /v1/alpha/search
  -> 返回模型文本 + results[] 结构化结果
  -> WebSearchItem 持久化并通过 app-server 投影
```

`web.run` 支持批量 `search_query`、`image_query`、`open`、`click`、`find`、`screenshot`，以及 finance、weather、sports、time 等命令。这里的 `click` 是对搜索服务返回的页面引用/链接执行服务端操作，不是点击用户浏览器里的按钮；`screenshot` 也属于搜索服务对可打开文档页面的能力，不能据此推断本地浏览器已被控制。

Standalone Web Search 的优势是：

- 作为普通 namespace tool 执行，可并行调用。
- 搜索结果会以 `results[]` 返回并持久化，当前结构至少包含 `ref_id`、URL、标题、snippet，便于客户端展示和证据转换。
- `web.run` 输出被标记为 external context，能与记忆和安全边界区分。
- 只有 OpenAI Provider 或使用 OpenAI actor authorization 的 Provider 且 Web Search 未关闭时才可用，不是任意模型都能免费调用。

### 5.2 搜索模式与约束

Codex 当前定义四种模式：

- `disabled`：不暴露 Web Search。
- `cached`：`external_web_access=false`，只使用缓存内容。
- `indexed`：只允许已被搜索索引收录的 URL，不任意实时抓取。托管 `web_search` 序列化为 `external_web_access=true` + `indexed_web_access=true`；Standalone `/alpha/search` 则使用 `external_web_access="indexed"`。
- `live`：`external_web_access=true`，允许实时外网访问。

还支持：

- `allowed_domains`：限定搜索域名。
- `location`：国家、地区、城市、时区。
- `context_size`：low / medium / high。
- 模型能力允许时返回文本或文本加图片。
- 企业 requirements 对可用搜索模式进行约束。

Codex 的 review 场景会强制关闭 Web Search，说明工具暴露应由具体用例控制，而不是全局永久开启。

### 5.3 Browser 插件不是 Web Search 的内部实现

开源 Codex 仓库新增了稳定 feature gate：

- `InAppBrowser`：允许桌面端内置浏览器面板。
- `BrowserUse`：允许 Browser Use Agent 集成。
- `BrowserUseFullCdpAccess`：允许更完整的 Chrome DevTools Protocol 表面。
- `BrowserUseExternal`：允许接入外部浏览器。
- `ComputerUse`：允许独立的 Computer Use 能力。

这些 gate 在源码中被标为 requirements-only。开源仓库还会发现 `chrome@openai-bundled` 和 `computer-use@openai-bundled`，但真正的浏览器运行时来自单独分发的插件，不在开源 `codex-rs` 中。本机 Browser 插件 manifest 的许可证为 Proprietary，因此可借鉴其合同和交互设计，不能直接复制实现。

Browser 插件通过 `browser-client` 暴露三类浏览器：

- `iab`：Codex/ChatGPT 内置浏览器。
- `extension`：通过扩展连接用户 Chrome，可复用用户已经打开或登录的页面。
- `cdp`：通过 Chrome DevTools Protocol 连接浏览器。

核心能力包括：

- 浏览器与会话：选择浏览器、命名 session、读取用户已打开标签页、claim 现有标签页。
- 标签页生命周期：list/new/selected/get/finalize、goto/back/forward/reload/close、handoff/deliverable。
- 页面理解：DOM snapshot、可见 DOM、截图、元素截图、页面 title/URL、console logs。
- 结构化交互：受限 Playwright locator，支持 click/fill/type/press/select/check/wait/file chooser/download。
- 通用交互：坐标 CUA 和 DOM node CUA，支持点击、双击、拖动、滚动、键盘和输入。
- 高级能力：受控 CDP、浏览器授权交接、剪贴板、文件下载。

因此，Codex **可以操作浏览器进行搜索**：它可以打开搜索引擎或站内搜索页面，填写查询框、提交、读取结果 DOM、点击候选页面并继续交互。Browser 插件说明也允许在没有更合适的 connector/API 时做一次聚焦的搜索引擎查询。

但 Browser 的规则明确要求：语义化操作优先使用 connector/API/CLI；浏览器主要用于用户明确要求 UI 操作、缺少专用接口、需要登录态、动态渲染或视觉验证的场景。它不应替代常规 Web Search。

### 5.4 Browser 的安全与生命周期设计

值得 Linnya 借鉴的不是某个具体 API 名，而是以下边界：

- 网页、截图、下载和 DOM 全部按不可信内容处理，不能让页面文本覆盖 Agent 指令。
- 发送表单、上传文件、购买、改权限、删除数据和输入敏感信息必须按动作确认。
- 不读取 cookies、localStorage、密码库或浏览器 profile 来“发现登录态”。
- CAPTCHA 需要用户确认，不能绕过付费墙或安全警告。
- 交互前先基于最新 DOM snapshot 确认 locator 唯一，再执行 click/fill；失败后刷新观察，不盲目重复。
- tab 与 browser binding 分离；tab 可以失效，browser session 仍可复用。
- turn 完成时区分清理、handoff 和 deliverable，避免无限积累标签页。
- Browser 优先使用受限 Playwright，坐标 Computer Use 只用于 DOM/locator 无法可靠覆盖的场景。

### 5.5 对 Linnya 的启示

- 模型供应商原生 Web Search 可作为独立 Provider，但它与模型账号、API 协议和计费强绑定。
- Standalone Search 的结构化 `results[]` 很适合映射到 Linnya Evidence，不过仍需转换成自己的 `[@ref]` 和可回放合同。
- 浏览器自动化必须独立于 `web_search` / `web_read`。浏览器侧“搜一下”是一个 UI workflow，不是 SearchProvider 实现。
- 浏览器搜索可以作为用户明确选择的真实场景，例如复用已登录站点搜索、企业内网页面或只提供 UI 的数据库；不能作为无 API 成本的默认搜索捷径。
- Linnya 可以借鉴 `Browser -> Tabs -> Tab -> Playwright/CUA/CDP` 的分层，以及 session/tab 生命周期，但应使用自己的公开 port 和安全策略，不能依赖 Codex 的专有插件协议。
- Codex 仍不是站点爬取参考实现。crawl 的队列、范围、预算、robots、去重和证据物化需要 Linnya 独立设计。

## 6. Linnya 当前能力与问题

### 6.1 已有能力

当前 `src/tools/web/` 已经提供：

- `web_search`：Provider 可替换，现有百度千帆和 Serper 实现。
- `web_read`：现有秘塔 Reader 实现。
- Model Catalog 通过 `web_search` / `web_read` capability 选择第一个启用 Provider。
- URL 规范化和基于 URL 的稳定短引用 `[@ref]`。
- 搜索结果与页面正文直接写入 EvidenceStore。
- 会话引用投影、hover、复制和另存到编辑器。
- `resource_read` 可通过 HTTP(S) URI 委托给 `web_read`。

这意味着下一阶段应扩展 Provider 和业务流程，不应重建 citation、投影或 EvidenceStore。

### 6.2 明确缺口

| 方面 | 当前状态 | 影响 |
| --- | --- | --- |
| 站点爬取 | 没有 crawl feature | 无法批量采集文档站或专题站 |
| 动态网页 | 不执行 JS，无浏览器会话 | SPA、登录页、交互页读取能力弱 |
| URL 安全 | 未看到统一的协议、私网 IP、重定向和域名策略 | 后续接本地抓取器时有 SSRF 风险 |
| 请求预算 | Provider HTTP 调用缺少统一超时、响应体、并发和取消合同 | 上游卡住时会拖长 Agent run |
| Provider 选择 | 取第一个 enabled 配置 | 缺少显式的用途、区域、成本和能力路由 |
| 可观察性 | 工具/Provider 仍有 `console.log`，供应商 request id 未统一进入工具事件 | 难以排查延迟、失败和费用 |
| 成本治理 | 没有每类能力的请求次数、页面数、字节数和供应商消耗账本 | 无法做额度和租户控制 |
| 内容治理 | 未形成 robots、版权、敏感域名和留存策略 | 企业场景存在合规风险 |

### 6.3 已有维护隐患

1. 历史上 `WebSearchTool` / `WebReadTool` 曾直接导入 Knowledge 目录下的 EvidenceStore，形成跨 domain 内部依赖。现在 Web 只拥有 capture DTO 与 `WebEvidenceWriter` 窄 port，由平台 ToolContext decorator 在 Host 组合边界映射 Evidence command；边界测试禁止 Web import Evidence domain 或其 ToolContext adapter。
2. `WebReadTool` 把长正文同时放进 `data.contentText`、`observation` 和 EvidenceStore。一次页面读取会多份持久化和传输同一正文，与工具规范中“长正文不要放进 data”相冲突。推荐让 EvidenceStore 保存全文，`data` 保存引用与统计，`observation` 只放受预算控制的正文窗口和续读 URI。
3. `findPriorWebSearchTitle()` 每次读取网页都会扫描当前会话全部 evidence bundle JSON。会话增长后，读取延迟会随文件数线性增加。标题关联应该由 Evidence 索引或 URL 查询 port 提供，不应在工具里遍历文件系统。
4. `resource_read` 目前直接实例化并调用 `WebReadTool`。这是迁移期委托方案，但继续增加 Web 行为会让统一资源工具依赖具体工具内部副作用。应逐步抽取 `read-web-page` orchestration，让 `web_read` 和 `resource_read` 共同调用它。
5. Serper、百度千帆、秘塔 HTTP adapter 没有统一超时和取消信号。这里不应通过层层 try/catch 兜底，而应在 HTTP port 的正式合同中定义 deadline、最大响应体和取消语义。

## 7. 推荐目标架构

### 7.1 Domain 边界

建议新增 `web-research` domain，负责“公开网页资料发现与证据获取”；浏览器自动化单独作为 `browser-automation` domain，不放进 Web shared。

建议结构：

```text
src/domains/web-research/
├── definitions/                 # 查询、页面、爬取、预算、结果合同
├── ports/                       # SearchProvider、PageReader、SiteCrawler、EvidenceWriter
├── shared/                      # 仅本 domain 复用的 URL 规范化与访问策略
└── features/
    ├── search-web/
    │   ├── functions/           # 查询规范化、结果去重、质量规则
    │   └── orchestration/       # 调用 SearchProvider，写入证据
    ├── read-web-page/
    │   ├── functions/           # 正文预算、元数据归一化
    │   └── orchestration/       # 调用 PageReader，写入证据
    └── crawl-website/
        ├── definitions/         # CrawlScope、CrawlBudget、进度事件
        ├── functions/           # URL 去重、范围判断、调度规则
        └── orchestration/       # 队列、并发、取消、断点与结果聚合

src/infra/adapters/web-research/ # Firecrawl/Tavily/Serper/Metaso 等外部实现
src/tools/web/                   # 模型工具薄适配，只调用公开用例
```

Evidence 如果被 Web、Knowledge Base、Deep Research 多方使用，应提升为独立稳定的 domain/public contract；如果暂时不迁移，则至少先提供窄小 `EvidenceWriterPort`，由 app-level orchestration 注入，避免 Web 直接依赖 Knowledge Base 内部文件。

### 7.2 统一合同

Provider 合同应按能力拆分，不设计一个大而全 `WebProvider`：

- `SearchProvider.search(query, options, deadline)`。
- `PageReader.read(url, options, deadline)`。
- `SiteCrawler.crawl(seed, scope, budget, progress, signal)`。
- 浏览器由单独 domain 暴露 `BrowserSession` 能力。

统一结果至少包含：

- canonical URL、title、snippet/content、site、published time。
- provider、request id、captured time。
- 内容类型、语言、最终 URL。
- 明确的失败类型：配置错误、访问策略拒绝、上游限流、超时、内容过大、解析失败。

工具层只把合同映射成 `StructuredToolResult`，不负责 HTTP、Provider 选择、抓取队列或正文摘要。

### 7.3 安全与预算硬约束

在本地抓取或浏览器能力上线前，必须先有：

- 只允许 `http` / `https`，禁止带用户名密码的 URL。
- DNS 解析后阻止 loopback、link-local、private、reserved、CGNAT 和云 metadata 地址。
- 每次重定向重新校验目标，不能只校验初始 URL。
- 域名 allowlist/blocklist，并明确策略配置错误是 fail-open 还是 fail-closed；企业管理策略应 fail-closed。
- 搜索结果数、单页字节数、页面正文字符数、crawl 页数/深度/总字节/总时长/并发上限。
- AbortSignal 贯穿 orchestration、port 和 adapter。
- HTML/PDF/图片等内容类型白名单；二进制不直接塞入模型上下文。
- robots 和站点条款策略，以及原文的留存时长和删除机制。

## 8. 方案选择与取舍

### 方案 A：供应商 API 优先

使用 Serper/百度做搜索，秘塔/Firecrawl/Tavily 做正文或爬取。

优点：开发快，正文清洗、反爬和代理由供应商承担；桌面端资源占用低。  
缺点：按量成本、供应商锁定、数据出境/隐私评估、额度和服务波动。  
适用：先把稳定联网研究能力交付给用户。

### 方案 B：本地开源抓取优先

使用本地 HTTP 抓取 + 正文解析，动态页面使用 Playwright/Chromium；搜索仍需独立数据源。

优点：正文和缓存可控，无正文解析 API 的逐次费用，适合内网或私有部署。  
缺点：代理、反爬、浏览器升级、验证码、资源占用和安全责任全部由 Linnya 承担；“没有 API 账单”不等于低总成本。  
适用：私有化、强数据控制、固定站点采集。

### 方案 C：混合能力路由（推荐）

常规搜索与静态正文使用 Provider API；明确需要 JS/登录/交互时，Agent 选择独立浏览器工具；批量站点采集走独立 crawl workflow。不同路径不做静默互相回退。

优点：覆盖面与成本较平衡，边界清晰，可按场景替换 Provider。  
缺点：需要统一证据、策略、成本与可观察性合同，初期架构工作比单一供应商多。  
适用：Linnya 这种既要普通对话联网，又要 Deep Research 和后续企业能力的产品。

## 9. 建议实施顺序

### Phase 0：修正现有边界

- 为现有三个 HTTP adapter 增加统一 deadline、取消和最大响应体合同。
- 建立 URL 安全/站点策略的 domain 能力。
- 把 EvidenceStore 调用收口到公共 port 或 app-level orchestration。
- 全文只在 EvidenceStore 保留一份；工具 `data` 返回 bundle/ref/统计，`observation` 返回预算窗口。
- 用结构化日志统一记录 provider、request id、耗时、结果数、字符数和失败类别。

### Phase 1：补齐 Provider 能力

- 保留百度/Serper/秘塔。
- 优先评估增加一个同时支持 read + crawl 的 Provider，Firecrawl 与 Tavily 二选一做正式验证，避免一次接入多个重叠供应商。
- 建立 Provider 能力声明和显式选择，不做请求失败后的跨供应商静默重试。
- 上线前实测中文搜索质量、英文搜索质量、PDF、新闻站、文档站、限流和单位成本。

### Phase 2：站点爬取 feature

- 独立 crawl job、预算、进度事件、取消、部分失败结果和断点。
- URL canonicalization、去重、站点范围与 robots 策略下沉到 functions。
- 每页先物化为 Evidence，再由单独的摘要/研究流程消费；抓取过程不直接做 LLM 总结。

### Phase 3：浏览器自动化

- 使用成熟的 Playwright/Chromium 能力，不自行实现浏览器协议。
- 采用 `BrowserSession -> Tab -> Playwright/DOM CUA/CDP` 分层；Playwright 为主，坐标操作只处理真实视觉交互场景。
- 会话、tab 生命周期、登录态、下载、截图、网络策略和用户审批归 `browser-automation` domain。
- 支持显式 claim 用户已有页面，但禁止直接读取 cookie、密码库或 profile；通过可控交互使用登录态。
- turn 结束时明确 close / handoff / deliverable，不让临时标签页和浏览器进程无限累积。
- 只给需要动态页面的场景暴露，不替代便宜的 `web_read`。
- 搜索引擎 UI 仅作为用户显式选择或没有 SearchProvider 的特定场景，不作为默认联网搜索实现。

### Phase 4：Deep Research 接入

- 通过请求作用域收缩/开放工具，不全局默认联网。
- Writer 只引用已经物化、可回放的 Web Evidence。
- 搜索、读取、爬取、浏览器步骤分别记录成本和来源，支持报告审计。

## 10. 验收重点

优先写业务导向的模块化端到端测试：

- 查询 -> 搜索结果 `[@ref]` -> 读取原文 -> Evidence 回放 -> 答案引用 -> 编辑器导出。
- URL 被安全策略拒绝时，不发出供应商请求，并产生可理解的工具错误。
- 站点爬取达到页面/字节/时间预算后可预测地停止，已完成页面仍可回放。
- 用户取消后，队列、HTTP 请求和浏览器会话全部停止。
- 单页部分失败、站点部分失败、供应商限流和超时在事件层可区分。
- 同一 canonical URL 不重复物化正文，搜索标题和页面标题的关联不扫描整个文件目录。
- 动态页面只在显式浏览器路径执行，普通静态页面不启动 Chromium。

## 11. 最终建议

Linnya 当前最值得投入的不是再造一个 `web_search`，而是把已有搜索/读取能力升级成一个边界清晰、可观察、可计费、可扩展的 `web-research` domain。

短期采用供应商 API 能最快获得稳定质量；中期补独立 crawl workflow；动态网页再通过独立本地浏览器能力覆盖。Hermes 可作为 Provider、预算和本地 Chromium 分层的参考；Codex 可同时作为原生/Standalone Web Search、浏览器 session/tab 生命周期和多交互表面的参考。但浏览器 UI 搜索不是免费的结构化搜索替代品，二者都不能直接替代 Linnya 自己的证据合同和跨 domain 架构。
