# 代码质量：不重复实现

一两句代码写得不好是小问题；同一件事在仓库里有好几份各自的实现是大问题。本文规定写新代码前怎么查、共享的东西放哪里、什么时候抽、用什么门禁防止回退。模块边界与 owner 规则见根目录 [AGENTS.md](../../AGENTS.md)，本文不重复。

## 1. 什么算大问题

评审和审计按这个顺序花力气：

- **大：同一条规则有两份以上实现。** 规则指用户或 Agent 能感知的行为：怎么显示时间、大小、数量；怎么把错误说给用户；名称怎么归一化；输出超长怎么截断。两份实现迟早不一致，用户看到的就是同一个产品里两种说法。
- **大：绕开 owner 自己做一遍。** 已有 domain、port、共享组件能做的事，在调用方重新实现：自己拼 SQL、自己起进程、自己算浮层位置、在纯函数里读 store 拿当前语言。
- **大：耦合方向反了。** 共享代码依赖业务模块；domain 之间 deep import 对方内部；Core 里出现具体插件的名字；循环依赖。
- **中：机械小工具到处抄。** `isRecord`、`clamp`、`sleep` 这类。单份没有危害，但每份都要各自测试，而且同名实现会悄悄分叉。
- **小：单处写法问题。** 命名、局部可读性。随手改，不是重点。

## 2. 写之前先查

新写一个函数、组合式函数或一段流程前，先确认它不是已有规则的又一份：

1. 按行为搜，不按名字搜。要显示时间，搜 `Intl.DateTimeFormat`、`昨天`，而不是只搜 `formatTime`。
2. 看第 3 节各共享位置 README 里的“已有能力”清单。共享位置每加一个能力，就在清单里加一行。
3. 找到了就用。不合用时改共享实现（加参数或修规则），不在调用方另写一份。
4. 没找到，再按第 4 节判断放共享位置还是留在本模块。

## 3. 共享的东西放哪里

判断只问两件事：谁要用（界面、Backend、插件），带不带界面。

| 内容 | 位置 |
| --- | --- |
| 界面、Backend 和插件都能用的纯函数：对象判断、数值与数组小工具、等待 | [`@linnya/foundation`](../../packages/foundation/README.md)：零依赖、无副作用、不读环境 |
| 跨进程数据合同，以及必须前后端一致的显示规则（例如历史时间） | [`@app/schemas`](../../packages/schemas/README.md) |
| 只给 Backend 的基础能力：文件、路径、进程、日志 | `src/shared/*` |
| 界面组件、浮层、定位、焦点、快捷键 | [`@linnya/renderer-ui`](../../packages/renderer-ui/README.md)；业务模块不自己监听全局点击、不自己算浮层位置 |
| 跟当前语言有关的显示：时间、数字、大小、排序比较 | [Renderer 本地化](../../apps/renderer/app/localization/README.md)；业务模块不直接调 `Intl` 和 `toLocale…` |
| 界面里与业务无关的非视觉逻辑 | `apps/renderer/shared` |
| 只在一个 domain 里复用 | 该 domain 的 `functions/`、`orchestration/`，不上移 |

共享目录不是杂物堆：每个文件一件事，文件名说清是什么事，README 清单里有它。

## 4. 什么时候抽，什么时候不抽

- **规则类：第二处出现就必须合并。** 规则只有一份，带测试；调用方不许微调后另存。
- **机械小工具：直接用 `@linnya/foundation`。** 里面没有就加进去，不在本文件现写。
- **可以留在本地的**：只服务这个文件的类型或数据结构、换个地方就没有意义的辅助函数。标准是它不表达产品规则，也不会有第二个调用方。
- **不要合并“长得像但原因不同”的代码。** 历史时间和待办截止日期都会写“昨天”，但一个说过去、一个说期限，是两条规则。合并的条件是：一个要改时，另一个也必须跟着改。
- **同名必须同规则。** 同一个名字在不同文件里行为不同（例如有的 `isRecord` 接受数组、有的不接受）比重复更危险；发现后先定规则，再统一名字。
- **共享函数的样子**：纯函数，`now`、语言这类环境从参数进来；带测试；调用方需要三个以上开关时，说明它其实是两件事，拆开。
- **不加只换名字的包装。** 包一层只为了让名字带上业务词，不要；需要补业务含义（例如没有值时显示“未知”）才包。
- **流程类重复同样处理。** 两个命令各写一遍“先给截断提示留空间、只输出完整的行”，应抽成一个编排，而不是只抽里面的小函数。

## 5. 门禁

共享实现建好不等于会被用，靠只减不增的基线拦住回退：

- **`pnpm run guard:shared-implementations`**：名单里的写法只能出现在它的共享位置。每统一一样东西，就把对应写法加进[名单](../../scripts/guards/shared-implementations/definitions/sharedImplementationRules.ts)；存量记在基线里，只许减少。新代码命中名单会失败，并提示该用哪个共享实现。清掉存量后运行 `pnpm run guard:shared-implementations:update` 收紧基线。
- 模块边界继续由现有各 `guard:*-boundary` 负责。

提交说明里写清新增了哪个共享能力，或者用了哪个已有的。评审看到新写的工具函数，先问第 2 节查过没有。

## 6. 全仓审计的方法与边界

- 先用[只读源码盘点](../../scripts/diagnostics/code-quality/README.md)固定范围和位置。生产源码、测试、开发脚本和生成物分开计量，记录明确排除项；不要把同名函数数、clone pair 数当成独立问题数。
- 同时找小函数和长流程：AST 函数体指纹用于完全相同的候选，专门的重复检测器补充改名、部分差异及跨语言片段。每次保留版本、配置和源码 commit；比例只在相同范围与参数下比较，不能靠增加无关代码稀释。
- 依赖图使用各运行面的正式解析配置，区分静态值导入、类型导入和动态加载；记录未解析的边。一个互相可达的模块组不是一个已复现的运行故障，树形组件递归和 parser 递归必须结合 owner 合同判断。
- 同步 I/O、空 catch、异步 store、全局点击监听是复核入口，不能直接批量替换。启动读取、SQLite 同步事务、生命周期清理与可取消等待各有自己的语义。
- 先确认调用方、输入、输出、默认值、失败与取消行为，再决定复用范围。相似的 schema 声明、平台 adapter 和独立测试不能为了降低比例被强行合并；规则相同的则应回到现有 owner。
