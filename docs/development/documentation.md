# Linnya 文档编写规范

本文规定公共仓中文档的写法、位置和维护方式。哪些内容可以进入公共仓，以[文档治理](../documentation-governance.md)为准；本文只回答稳定文档应怎样落到代码树中。

## 1. README 写作规范

### 1.1 什么时候需要 README

出现以下任一情况时，应在对应 owner 目录编写或更新 README：

- domain、feature、package、app 或 app-level orchestration 有独立且长期稳定的职责边界；
- 调用方需要从公开入口、schema、port、registry 或 contribution 中选择正确入口；
- 模块包含多个目录或步骤，只看文件名无法理解主调用链、事实 owner 或生命周期；
- 模块存在容易误用的安全、权限、持久化、跨进程或跨平台约束；
- 新贡献者很可能从该目录开始阅读，需要一份不依赖内部过程记录的导航。

以下情况通常不单独新增 README：

- 目录只有一个职责直白的文件，且其类型和命名已经完整表达合同；
- 内容只是阶段计划、调研过程、完成清单、测试记录或发布证据；
- 只是重复父级 README、代码注释或 schema 已经说明的字段；
- 为了按主题分类而创建一个只容纳单篇文档的顶层 `docs/<topic>/` 目录。

已有 owner README 时优先更新它，不为同一模块建立第二个“总览”真源。

### 1.2 README 放在哪里

- 模块 README 放在其 owner 根目录，例如 `src/domains/<domain>/README.md`、`packages/<package>/README.md` 或 `apps/<app>/README.md`。
- feature 只有在具备独立业务能力、合同或生命周期时才拥有自己的 README；纯技术子目录由上级 README 导航即可。
- 单一模块只有一篇架构、协议或来源治理文档时，默认融合进 owner README，避免产生容易被遗漏的第二入口。
- 只有存在多个职责独立、需要分别维护的专题，或单篇内容面向明显不同的读者和维护周期时，才建立 `<owner>/docs/`；owner README 必须说明每篇专题的用途。
- 真正横跨多个 owner 的产品级长期规范放在仓库根 `docs/`；根 `docs/` 不承担模块文档的分类镜像。
- 文档应跟随事实 owner 移动。目录调整后必须同时更新入口、反向引用和文档门禁。

### 1.3 README 的基本结构

README 不要求套用固定模板，但通常按以下顺序回答问题：

1. **定位**：用一到两段说明模块是什么、服务谁，以及唯一 owner 是什么。
2. **负责与不负责**：明确边界，特别指出相邻模块中容易混淆的职责。
3. **目录或修改地图**：说明主要子目录、公开入口和“要改某件事先去哪里”。
4. **核心合同或流程**：只描述理解模块所需的不变量、身份、数据流和生命周期。
5. **依赖与协作**：说明允许的依赖方向，以及跨 domain、跨进程或跨 package 的连接方式。
6. **验证方式**：列出该 owner 最小而真实的测试、构建或检查入口。
7. **延伸阅读**：链接模块内专题文档和相邻 owner，不复制其内容。

小模块可以合并或省略不适用的章节。README 的目标是让读者找到正确 owner 和入口，不是把所有实现细节写成教程。

### 1.4 README 的内容要求

- 写当前稳定事实和约束，并解释关键设计“为什么”；历史过程留给 Git history 或私有过程文档。
- 类型、字段和行为以 schema、public contract 与 owner 实现为准；README 应引用入口，不手抄大段代码。
- 使用仓库内相对路径链接，不写开发者绝对路径，也不依赖相邻 checkout、私有仓或本机环境。
- 同一规则只保留一个详细 owner；其他 README 用一句上下文和链接指向它。
- README 不维护通用第三方依赖清单、许可证正文或来源台账。依赖与版本以 package manifest、lockfile 为准，法定署名与许可文本由根
  `THIRD_PARTY_NOTICES.txt` 和发布门禁承接；只有许可证会直接改变该模块的开发、链接或分发方式时，才在 README 写最小必要约束。
- 文档中的命令必须能从仓库根或明确写出的工作目录执行，并说明必要前置条件。
- 不承诺尚未实现的能力。未来方向只有已经成为公开产品合同且不会泄露内部决策时才写入。

## 2. 模块专题文档

当模块已经存在多个职责独立的专题，或内容具有与 README 明显不同的读者和维护周期时，才拆到模块内 `docs/`。典型内容包括成组的协议规范、平台差异系列，以及多篇故障排查指南。只有一篇专题时优先通过清理重复、缩短细节和完善目录把它融合进 README，不能只因篇幅较长就新建 `docs/`。

专题文件名必须表达主题，例如 `architecture.md`、`source-acquisition.md`，避免 `notes.md`、`misc.md`、`new-design.md` 等依赖时间或上下文的名称。专题文档开头应说明它补充哪个 owner README，以及哪些事实仍以代码合同为准。

拆分后，README 仍需保留足够的定位、边界和入口；不能只留下一个没有上下文的链接列表。

## 3. 产品级文档

只有下列内容适合放在根 `docs/`：

- 产品定义、公开历史和长期愿景；
- 整个仓库的工程、开发、贡献和文档规范；
- 同时约束多个独立 owner、无法合理归属单一模块的正式架构；
- 插件平台、Conversation Platform 等产品级系统的统一入口。

如果一篇文档只解释一个 domain、feature 或 package，即使它引用了多个调用方，也应优先归入该 owner，而不是在根 `docs/` 建立同名目录。

## 4. 链接、路径与示例

- 仓库内 Markdown 链接使用相对路径，并在移动文档后验证目标和标题锚点仍存在。
- 代码路径使用仓库相对路径，例如 `src/domains/commands/`；禁止出现 `/Users/<name>/...`、`C:\\Users\\<name>\\...` 或某台开发机的盘符路径。
- 跨仓依赖只链接正式公开地址，并保证当前仓在离线、没有相邻 checkout 时仍可构建和理解。
- 示例中的账号、域名、密钥、目录和数据使用明显的虚构值；不要把真实本机信息“脱敏一半”后保留。
- 删除或移动文档前先用全文搜索找出入口、反向引用、脚本白名单和文档门禁。

## 5. 更新与检查

架构、目录、公开合同、开发流程或支持范围变化时，必须在同一次改动中更新 owner README 和相关专题文档。提交前至少检查：

1. 新增内容是否写在唯一 owner，而不是复制到多个总览；
2. README 是否能回答定位、边界、入口和验证方式；
3. 所有本地链接和代码路径是否有效；
4. 是否残留旧目录名、绝对路径、内部过程信息或私有仓依赖；
5. 文档是否描述当前实现，而非已过期方案或尚未落地的计划。

自动门禁可以检查死链、路径泄露、旧路径和结构一致性，但不应通过 README 快照锁定措辞。内容正确性仍由改动 owner 在代码审阅中负责。
